# План релизов, обновлений и удалённой поддержки

Цель: превратить "Голос" из локальной разработки в программу, которую можно поставить на другой Windows-компьютер, обновлять через GitHub и получать диагностику без ручного копания в файлах пользователя.

## Решение

Делать стоит, но поэтапно.

Сначала используем GitHub Releases как источник EXE и обновлений. Это проще, дешевле и безопаснее, чем сразу поднимать свой сервер. После этого добавляем ручную отправку диагностики. Свой сервер нужен следующим этапом, когда появятся несколько пользователей, подписка, прокси для OpenAI или удалённая панель поддержки.

## Этап 0. Текущий MVP

Статус: сделано.

Что уже есть:

- запуск из Python;
- Windows tray;
- окно настроек;
- профили распознавания;
- локальное распознавание;
- OpenAI-распознавание через ключ пользователя;
- GPT-исправление текста;
- сбор диагностики в zip;
- GitHub-репозиторий как источник проекта.

Готово, когда:

- F8 записывает голос;
- текст вставляется в активное окно;
- настройки открываются из tray;
- диагностика собирается без секретов.

## Этап 1. EXE и GitHub Releases

Цель: получить понятный файл для установки/запуска на другом компьютере.

Что делаем:

- добавляем версию программы, например `0.1.0`;
- проверяем сборку `build_exe.ps1`;
- добавляем `package_release.ps1` для подготовки release-архива, `sha256` и `latest.json`;
- формируем архив `Golos-win64.zip`;
- публикуем GitHub Release;
- прикладываем к релизу:
  - `Golos-win64.zip`;
  - `latest.json`;
  - `sha256`-контрольную сумму;
  - краткую инструкцию установки.

Готово, когда:

- на другом Windows-компьютере можно скачать архив из GitHub Release;
- программа запускается без Python;
- пользователь видит версию программы в настройках;
- в README есть инструкция установки через релиз.

## Этап 2. Проверка обновлений

Цель: программа сама сообщает, что вышла новая версия.

Важное условие: `latest.json` должен быть доступен приложению без GitHub-авторизации. Если репозиторий или GitHub Release приватные, обычный пользовательский EXE не сможет скачать `latest.json` напрямую. В таком случае нужен публичный release-репозиторий, GitHub Pages/static URL или наш сервер обновлений.

Статус: в работе. Базовая проверка обновлений через публичный `latest.json` добавлена в окно настроек и CLI.

Что делаем:

- во вкладке "Обновления" показываем текущую версию;
- добавляем кнопку `Проверить обновления`;
- программа читает `latest.json` из GitHub Release или стабильного URL;
- если версия новее, показывает кнопку `Скачать`;
- скачанный файл проверяется по `sha256`;
- установка пока может быть ручной: открыть папку со скачанным архивом.

Готово, когда:

- старая версия видит новую;
- пользователь понимает, что обновление доступно;
- файл скачивается;
- контрольная сумма совпадает;
- при ошибке пишется понятное сообщение в лог.

## Этап 3. Ручная отправка диагностики

Цель: пользователь может сам отправить безопасные данные для разбора ошибки.

Статус: сделано как ручное GitHub-обращение. Программа создаёт diagnostic ZIP, текст обращения, открывает GitHub Issue и папку с архивом. ZIP пользователь прикрепляет сам.

Что делаем:

- оставляем текущий `Собрать диагностику`;
- добавляем кнопку `Отправить диагностику`;
- добавляем CLI `--prepare-support-request`;
- перед отправкой создаём текст обращения с путём к архиву;
- отправляем только безопасный zip:
  - `logs/app.log`;
  - очищенный `config.yaml`;
  - версия программы;
  - версия Windows;
  - выбранный профиль;
  - технические ошибки;
- не отправляем:
  - `.env`;
  - OpenAI API key;
  - временное аудио;
  - скачанные модели;
  - приватные ключи;
  - полный распознанный текст без отдельного согласия.

На первом шаге отправлять можно:

- вручную в GitHub Issue;
- вручную файлом в Telegram/почту;
- или через простой private endpoint на нашем сервере.

Готово, когда:

- пользователь нажимает одну кнопку;
- диагностика создаётся;
- открывается GitHub Issue и папка с ZIP;
- в интерфейсе видно `Диагностика готова` или понятная ошибка;
- секреты не попадают в архив.

## Этап 4. Сервер поддержки

Цель: видеть ошибки пользователей централизованно и готовить основу для подписки/прокси OpenAI.

Статус: базовый серверный каркас добавлен в `support_server/`. Боевой деплой на VPS, домен, HTTPS и постоянный сервис остаются отдельным шагом.

Минимальная архитектура:

- VPS;
- HTTPS;
- backend на FastAPI;
- SQLite на первом шаге, PostgreSQL позже при росте;
- папка/объектное хранилище для диагностических архивов;
- простая админка только для владельца.

Минимальные endpoints:

```text
GET  /health
POST /api/diagnostics
POST /api/events
GET  /api/update
```

Что хранить:

- installation id;
- версия программы;
- версия Windows;
- выбранный профиль;
- дата последнего запуска;
- последние ошибки;
- диагностические архивы;
- статус обновлений.

Что не хранить:

- OpenAI API key пользователя;
- временное аудио;
- распознанный текст по умолчанию;
- пароли, токены, приватные файлы.

Готово, когда:

- программа отправляет диагностику на сервер, если задан `support.server_url`;
- сервер принимает файл и сохраняет запись в SQLite;
- владелец видит список установок и ошибок;
- доступ к админке закрыт паролем или токеном.

## Этап 5. Автоматическое обновление

Цель: пользователь нажимает `Обновить`, программа сама заменяет файлы.

Что делаем:

- отдельный маленький updater;
- основной "Голос" скачивает новую версию;
- проверяет `sha256`;
- запускает updater;
- updater закрывает "Голос", заменяет файлы и запускает новую версию.

Важно:

- не обновляться без согласия пользователя;
- не запускать скачанный файл без проверки контрольной суммы;
- не ломать `.env`, `config.yaml`, логи и пользовательские настройки.

Готово, когда:

- старая версия обновляется до новой без ручной распаковки;
- после обновления сохраняются настройки;
- при ошибке updater оставляет старую рабочую версию.

## Этап 6. OpenAI: ключ пользователя или сервер-прокси

Есть два режима.

### Вариант A. Ключ пользователя

Пользователь вводит свой OpenAI API key в программе.

Плюсы:

- дешевле для нас;
- проще юридически и финансово;
- пользователь платит сам за своё использование.

Минусы:

- пользователю нужно создать ключ;
- нужно безопасное окно ввода ключа;
- ключ хранить только локально в `.env` или защищённом хранилище Windows.

### Вариант B. Сервер-прокси OpenAI

Программа отправляет аудио/текст на наш сервер, сервер вызывает OpenAI.

Плюсы:

- пользователь не видит API key;
- можно сделать подписку;
- можно централизованно менять модели и лимиты.

Минусы:

- дороже;
- выше ответственность за приватность;
- нужно хранить лимиты, пользователей, оплату и защиту от злоупотреблений.

Рекомендация:

- сначала оставить ключ пользователя;
- сервер-прокси делать только после этапов 1-5;
- если делать прокси, сразу добавить лимиты, авторизацию, журнал расходов и правила хранения данных.

## Этап 7. Удалённые команды

Удалённые команды делать осторожно.

Разрешить можно:

- запросить диагностику при следующем запуске;
- попросить пользователя подтвердить отправку;
- предложить обновление;
- переключить канал обновлений только после согласия.

Не делать на раннем этапе:

- удалённо запускать команды Windows;
- удалённо читать произвольные файлы;
- удалённо менять настройки без подтверждения;
- включать микрофон или запись без действия пользователя.

Готово, когда:

- сервер может поставить флаг `нужна диагностика`;
- программа показывает пользователю запрос;
- пользователь подтверждает;
- диагностика отправляется.

## Ближайший порядок работ

1. Добавить версию программы в код и окно настроек.
2. Довести `build_exe.ps1` до стабильной release-сборки.
3. Собрать `Golos-win64.zip`.
4. Создать GitHub Release `v0.1.0`.
5. Добавить `latest.json` и `sha256`.
6. Реализовать кнопку `Проверить обновления`.
7. Реализовать ручную отправку диагностики.
8. После этого проектировать сервер поддержки.

## Правила безопасности

- Никогда не коммитить `.env`.
- Никогда не зашивать OpenAI API key в EXE.
- Диагностика по умолчанию не содержит аудио и распознанный текст.
- Любая отправка на сервер должна быть видима пользователю.
- Обновления устанавливаются только после проверки источника и контрольной суммы.
- Старую рабочую версию нельзя удалять до успешной установки новой.
